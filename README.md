# MiniPrinter · ESP32 蓝牙热敏打印机

用一颗 ESP32 驱动 384 点热敏机芯，配一个自制的 Android App：
选图/排版 → BLE 传输 → 逐行加热打印，并支持**通过蓝牙给打印机升级固件**（双分区 OTA）。

> 这个项目不是"跑个 demo"。核心难点在**热敏头的能量控制**：热敏纸是阈值型器件，
> 能量不足不出色、过量则折损发热体寿命。项目里有一套按规格书推导、并针对这颗
> 拆机头实测校正过的能量模型（冷态补偿 + 热积累前馈 + 点密度补偿 + 统一钳位）。

## 硬件平台

- 主控：ESP32（双核，BLE 4.2）
- 打印头：384 点热敏机芯，6 组 × 64 点分时选通，内置 NTC 测温
- 走纸：2 相 4 线步进电机 + H 桥驱动
- 电源：锂电池，升压至 7.2V 供打印头，打印时开、结束即关

> 具体器件型号、引脚分配、原理图与 PCB 不在本仓库范围内，这里只放软件。

## 系统架构

### 固件：三层，一个文件一件事

```
firmware/src/
├── main.cpp            只做初始化 + 创建 3 个任务，顶部有完整架构注释
├── config.h            全部编译期常量（引脚 / 能量 / 时序 / 温度 / 版本号）
│
├── hal/                硬件抽象层：直接碰 GPIO / SPI / ADC / BLE
│   ├── printer       打印头门面：一行怎么切拍、哪个拍点哪几组
│   ├── printhead     STB 选通、SPI 送 48B、单组加热、质量参数
│   ├── vh            升压开关、延迟断电、强制断电
│   ├── thermal_guard 两级热锁存（作业级 + 跨作业级）
│   ├── motor         8 拍相序、1-2 相/双相、走纸节拍
│   ├── sensor        门面：begin / update
│   ├── thermistor    NTC 换算 + 滤波 + 故障判定
│   ├── battery       电压采样 + 放电曲线 → 百分比
│   ├── paper         缺纸检测 + 去抖
│   ├── button        去抖、短按/长按事件
│   ├── led           非阻塞闪烁状态机
│   └── ble           GATT 服务、连接回调、transport_send
│
├── app/                应用层：状态机与任务编排
│   ├── runtime        ★ 17 个跨任务全局状态集中定义
│   ├── command        命令分发 + 作业四个出口（结束/暂停/清场/上报）
│   ├── job.h          打印任务入口
│   ├── task_print     任务骨架：只做循环、OTA 冻结、按 jobState 分发
│   ├── job_idle       空闲分支：自检 / 走纸 / 长按连续出纸
│   ├── job_overheat   过热暂停分支：断电、等降温、断点续打
│   ├── job_run        运行分支：三道体检、取行打印、收尾判定
│   ├── task_button    按键任务
│   ├── task_monitor   采样 / 补偿刷新 / 状态上报
│   └── selftest/      诊断页，一页一个文件（draw + 6 个 page_*）
│
└── core/               纯逻辑层：不碰硬件，可以脱板阅读
    ├── protocol       帧编解码（AA 55 + type + len + payload + CRC）
    ├── heat_model     能量策略：热积累前馈 / 冷头补偿 / 点密度补偿 / 统一钳位
    ├── temp_comp      规格书表 4 的温度系数查表
    ├── crc32          增量 CRC32（IEEE）
    ├── ota            OTA 会话：序号、ACK、超时、abort
    └── ota_flash      Update 库的唯一封装 + 分区信息
```

**分层约定**：`task_*` 只做调度（循环 / 分发 / 让出），`job_*` 只做业务，两者不混；
`core/` 不许 include `hal/`。这条约束是为了让"改浓度"和"改走纸"互不牵连。

### 一次打印的数据流

```
App  →  BLE  0x02 PRINT_DATA（4 行/包，48B×4）
     →  core/protocol      校验 + 入队（48 行环形队列）
     →  app/job_run        从队列取一行
     →  hal/printer        切拍：1-2 相 4 拍（每拍 2 组）/ 双相 2 拍（每拍 3 组）
          ├── core/heat_model  这一组该加热多少 µs
          ├── hal/printhead    SPI 送 48B → 拉 STB → 该组 64 点同时发热
          └── hal/motor        走一拍（0.03125mm）
     →  app/command        每 200ms 上报 STATUS（已打印行数，App 据此流控）
```

### 任务与分核

| 任务 | 核 | 优先级 | 职责 |
|---|---|---|---|
| `print` | core1 | 5 | 打印 / 自检 / 走纸，行内不让出（微秒时序），每 8 行让 1 tick |
| `button` | core1 | 3 | 10ms 采样去抖，只投递事件 |
| `monitor` | core0 | 2 | 20/100ms 采样头温、电池、纸张；刷新温度补偿；上报状态 |
| `ota` | core1 | 4 | 独占 flash 写入，BLE 回调只入队 |

## 关键设计

### 1. 能量模型：为什么是 3600µs

机芯规格书给的是：E0 = 0.20 mJ/dot，P0 ≈ 0.247 W/dot @VH 7.2V，
25℃ 推荐 Ton = 540µs（条件是 64 点同时加热）。按标称折算，安全上限约 800µs。

**但这颗拆机头在 800µs 下 27℃ 几乎不出色。** 逐项排查后确认不是"VH 只有 3.3V"
（实测 7.2V）、不是 STB 电平不足（FPC 逻辑端接 3V3，VIH 满足），更可能是拆机头
回路阻抗偏大 / 带载压降 / 行周期远慢于 S.L.T 1.25ms 导致散热过多。因此本项目
**在明知超额定（3600µs ≈ 4.45×E0）的前提下运行**，并用三层机制把风险压到可控：

| 机制 | 作用 | 依据 |
|---|---|---|
| 温度补偿（表 4） | 5/25/45℃ = 1.231 / 1.000 / 0.846，>45℃ 不外推 | 规格书表 4 斜率 −0.74%/℃ |
| 冷态起步补偿 | 冷头 ×1.25，随热状态平滑退出 | 实测冷态发色阈值更高 |
| 热积累前馈（开环） | 逐行按「黑点数 × 实际脉宽 × repeat」累积热状态 s，一阶指数精确解冷却（τ≈64 行≈2s），稳态最多削 15% | 解决"开头灰、越打越黑" |
| 硬上限 | `HEAT_US_ABS_MAX = 4000 × 1.25 = 5000µs`，三条分支统一在最后一步钳位 | 防止补偿叠加失控 |

关键点：**这是开环前馈，不是闭环**。不测打印结果、不算误差、不反馈校正，
只把"已经往头里灌了多少能量"当作热状态的代理。

> 早期版本有个反向 bug：点补偿分支单独钳 4000，导致"加深档"在实心黑块上
> 反被钳回 4000，比"标准档"的 4600 更淡 —— 档位语义反了。现在改成单一出口，
> 三条分支都在最后一步按 `HEAT_US_ABS_MAX` 钳位，绝不提前 return。

### 2. 热保护：50℃ 熔断 + 断点续打

- 保护线取规格书表 1 的**工作温度上限 50℃**（不是表 3 的 65℃ 永久损坏线），
  45℃ 恢复；NTC 失效同样拒绝打印。
- 打印中触发时**不杀作业**：`jobState=3` 暂停 → 关 VH、释放打印头、停走纸，
  但保留队列、`doneLines`、电机相位，并冻结 3 秒断流超时；降到 45℃ 从下一行续打。
- 只有 NTC 失效或冷却超过 3 分钟才真正中止并上报错误。
- 续打时保存/恢复热状态 s 与冷头补偿，否则纸上会留一道浓淡分界。

### 3. VH 时序（规格书 3.7）

作业开始 → 先把 STB 全部拉低 → 开 VH → **等 1000ms** 让升压建立 → 开始加热；
作业结束立刻关断。`vh_force_off()` 是唯一能保证"现在就断电"的接口，
行级熔断、进入暂停、暂停期间每轮、作业结束、BLE 断连五处都调用它（幂等）。

> 之前漏了这条：熔断时只"不拉 STB"，VH 还带电，头温降不下来 —— 用户实测
> "断连重连后一直不降温"就是这个原因。

### 4. BLE OTA：双分区 + 停等 ACK

分区表用 ESP32 默认 4MB 方案，天生有 `otadata + app0 + app1`（各 1.25MB），
**不需要专用 bootloader**：OTA 就是"运行中的 app 写另一块分区"。

- 一块 = `seq(2B) + 238B 数据`，整帧 244B 正好等于 MTU 247 的单次写上限（单片无碎片）
- 每 16 块停等一次 `OTA_ACK`，应答里的 `next_seq` 直接暴露缺口，App 从那里补发
  （丢中间块、丢最后一块走同一条路径，不需要单独的 NACK 分支）
- 双端 CRC32(IEEE)：App 算全镜像，固件算**实际写进 flash 的字节**，收尾比对
- 失败/超时/断连只 `Update.abort()` —— **otadata 不变，当前固件完好**
- 写 flash 全在独立 `otaTask`，BLE 回调只做序号校验 + 入队，不阻塞协议栈
- 双分区严格交替 app0 ↔ app1，只保留上一版；想回退要推回旧 `.bin`

### 5. 流控与速度

一行 6 组 STB 是**串行**加热（每组 ~3800µs），所以瓶颈在加热不在电机。
App 不再按估算行时间空等，改为纯 `doneLines` 流控（固件 48 行队列，
保持未打印行数 ≤32）；整组全白时跳过选通，稀疏文本行速度快一倍以上。

## 构建与烧录

### 固件（PlatformIO）

```bash
# 环境：Python + PlatformIO Core，ESP32 平台包
pio run -d firmware                 # 编译
pio run -d firmware -t upload       # 串口烧录
```

> **踩坑**：工程路径含中文或空格时，xtensa 链接器创建 `firmware.map` 会报
> `Permission denied` / `Invalid argument`。`platformio.ini` 里因此把
> `build_dir` 指到 `$USERPROFILE/pio_build/printer`（纯英文路径，变量展开，
> 不会写死个人目录）。工程路径本来是纯英文的话，删掉那一行即可。

**两种镜像不能混**：

| 文件 | 首字节 | 用途 |
|---|---|---|
| `firmware/merged_firmware.bin` | `0xFF` | 含 bootloader + 分区表，**只**用串口烧到 `0x0` |
| `firmware_ota.bin` | `0xE9` | 纯 app 镜像，**只**给 App 里的 OTA 用（App 会拒绝 `FF` 开头的包） |

### Android App

```bash
JAVA_HOME="<你的 JDK 路径>" ./gradlew assembleDebug
# 产物：app/build/outputs/apk/debug/app-debug.apk
```

minSdk / targetSdk 见 `app/build.gradle`。依赖 Material 3（`material:1.7.0`），
其中显式抬了 `constraintlayout:2.1.3` 以适配离线缓存。

App 侧代码只有 5 个文件：

| 文件 | 职责 |
|---|---|
| `MainActivity.kt` | 界面、参数下发、打印流控、OTA 流程、自动重连 |
| `ble/PrinterBle.kt` | GATT 连接、MTU 协商、写队列、扫描过滤 |
| `ble/PrinterProtocol.kt` | 帧编解码、命令组帧、事件解析 |
| `image/BitmapConverter.kt` | 缩放/裁剪、二值化（文字阈值 / 图片 Floyd–Steinberg）、输出 1bit |
| `image/TextRenderer.kt` | 文本排版与点阵渲染 |

## 已知限制与未验证项

工程上没做完的部分，写在这里而不是藏着：

1. **长期超额定运行**。默认 3600µs 是 E0 的 4.45 倍，"质量最强"档（repeat=2）
   叠加后可达 8.9–11 倍，占行周期 13.8–15.7%（规格书表 2 额定 ≤12.5%）。
   50℃ 熔断只防"累积热失控"，防不了"单脉冲过能量"，长期打大面积黑图会折损
   发热体寿命。这是为让这颗拆机头出色而做的取舍，不是合规设计。
2. **质量档位（标准/加深/最强）是自定义的**。规格书里没有"质量档位"这个概念，
   只给了 540µs 等推荐值；三档的预加热/重复遍数/点密度补偿数值是实测调出来的。
3. **自动回滚未启用**。默认 bootloader 没开
   `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`，`esp_ota_mark_app_valid_cancel_rollback()`
   返回不支持后被忽略。所以兜底是"失败不改 otadata"+"串口烧回备份"，
   不是"启动失败自动回退"。唯一兜不住的情况：新固件能启动但 BLE 挂了，
   只能串口救。
4. **PIN 级验证的状态**。所有功能都通过编译与静态核对，但以下只做过代码级验证、
   未在真机复测：BLE OTA 完整流程的边界（断电、超时）、LED 指示、Material 3 界面观感、
   OTA 后自动重连、电量百分比显示。
5. **5 个诊断页没有 App 入口**。整页自检 / 负载页 / 压力测量 / 原工程复刻 / 走纸标尺
   只能通过串口命令触发；App 只开放了"点检"。
6. **能量模型未做温度标定曲线**。表 4 的 −0.74%/℃ 是线性近似，
   这颗拆机头在低温和高温段的实际曲线更陡，补偿只能算"有依据的保守估计"。
